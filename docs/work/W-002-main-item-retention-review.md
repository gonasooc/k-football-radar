# W-002 · 보존 상한 인상 검토

- 상태: 진행 중
- 최근 갱신: 2026-09-21
- 관련 문서: [docs/README.md](../README.md), [docs/plan.md](../plan.md), [lib/item-retention.ts](../../lib/item-retention.ts), [docs/work/W-001-main-docs-structure.md](W-001-main-docs-structure.md)

## 현재 상황

보존 상한(주요 4,000 / 보조 700 / 유튜브 500)을 올려야 하는지 검토해 달라는 요청이다. 2026-09-21 기준 저장된 5,044건으로 실제 사용량, 유입량, 인상 비용을 측정했다.

핵심 결과는 세 버킷의 상황이 서로 달랐다는 것이다. 주요 항목은 상한이 아니라 90일 창이 먼저 걸려 상한만 올려도 달라지지 않고, 보조 항목은 20일, 유튜브는 45일치만 남아 상한이 실제로 자르고 있었다. 인상 비용은 작았다.

2026-09-21에 C안(6,000 / 3,400 / 1,200)을 적용하고, 밀려난 과거 뉴스 2,701건도 Git 이력에서 복구했다. 저장 항목은 5,044 → 7,745건이 됐고 `전체` 범위는 20일에서 55일로 늘었다. 검증은 모두 통과했다.

- 완료 조건: 상한 변경과 복구가 운영에 반영되고(push 후 다음 수집 실행), 관련 문서가 새 값과 일치한다.
- 사람이 판단할 사항: 유튜브 과거 구간을 수동 수집으로 다시 채울지. 보조 범위를 55일보다 더 늘리려면 상한을 한 번 더 올릴지도 함께 본다.

## 진행과 판단

### 배경과 범위

제품 정책은 발행 90일 보존이지만, 실제로는 종류별 건수 상한이 먼저 걸려 버킷마다 보이는 기간이 다르다. 이번 작업은 측정과 권고까지이고, 값 변경은 결정 후에 한다.

### 측정 결과

2026-09-21 기준. ‘유입량’은 상한에 잘리지 않은 구간만 사용했다(가장 오래된 날짜는 일부만 남아 있어 제외).

| 버킷 | 보유 / 상한 | 실제로 보이는 기간 | 무엇이 먼저 거는가 | 유입량 |
| --- | --- | --- | --- | --- |
| 주요 뉴스·공식 | 3,844 / 4,000 (96%) | 89.9일 | 90일 창 | 43.2건/일(90일 평균) |
| 보조 뉴스 | 700 / 700 (100%) | 20일 | 상한 | 35.1건/일 |
| 유튜브 | 500 / 500 (100%) | 45일 | 상한 | 11.2건/일 |

- 주요 항목의 상한 여유는 156건(4%)뿐이다. 지금은 창이 먼저 걸리지만 유입이 조금만 늘어도 상한이 먼저 걸린다.
- 유입량은 시기에 따라 크게 흔들린다. 일평균 주요 항목이 2026-07은 85.6건, 2026-08은 28.4건, 2026-09는 13.4건이다. 7월 수준이 돌아오면 90일을 채우는 데 약 7,800건이 필요하다.
- 90일을 온전히 채우려면 현재 유입 기준으로 주요 약 3,900건, 보조 약 3,200건, 유튜브 약 1,100건이 필요하다.

### 인상 비용

| 항목 | 현재(5,044건) | 3배 규모 추정 |
| --- | --- | --- |
| R2 snapshot 크기 | 6.27 MiB (항목당 약 1,303 bytes) | 약 18.6 MiB |
| 전체 Zod 검증 | 33 ms | 약 100 ms |
| SHA-256 계산 | 6 ms | 약 20 ms |
| `createFeedContext` 파생 계산 | 174 ms | 439 ms (실측, 거의 선형) |

항목 수를 2배·3배로 늘려 측정했을 때 파생 계산은 1.69배·2.53배로 선형에 가깝다. 제곱으로 늘어나는 구간은 없었다. 이 계산은 snapshot당 한 번, 요청 뒤에서 수행된다.

### 선택지

| 선택지 | 상한 | 보이는 기간 | 예상 항목 수 / snapshot |
| --- | --- | --- | --- |
| A. 유지 | 4,000 / 700 / 500 | 90일 / 20일 / 45일 | 5,044건 / 6.3 MiB |
| B. 단계적 인상 | 4,500 / 2,000 / 900 | 90일 / 57일 / 80일 | 약 6,800건 / 8.4 MiB |
| C. 90일 정합 | 6,000 / 3,400 / 1,200 | 세 버킷 모두 90일 | 약 8,500건 / 10.6 MiB |

**2026-09-21 결정: C안을 적용했다.**

권고는 C였다. 제품 정책이 90일 보존인데 `전체` 범위와 유튜브만 20일·45일에서 잘리는 지금 상태가 문서·UI와 어긋나고, 비용은 snapshot 4.3 MiB와 파생 계산 약 100 ms 증가에 그친다. 7월 같은 뉴스 급증기까지 주요 항목을 방어하려면 주요 상한을 8,000으로 잡아야 하지만, 그 구간에서는 90일 창을 포기하고 최신성만 유지하는 선택도 가능하다.

### 적용 내용

1. [lib/item-retention.ts](../../lib/item-retention.ts)의 `DEFAULT_MAX_RETAINED_ITEMS` 4,000 → 6,000, `DEFAULT_MAX_RETAINED_SECONDARY_ITEMS` 700 → 3,400, `DEFAULT_MAX_RETAINED_YOUTUBE_ITEMS` 500 → 1,200. 수집 워크플로에 보존 관련 환경변수가 없어서 운영에 실제로 적용되는 값은 이 기본값이다.
2. [.env.example](../../.env.example)의 값과 설명을 같은 값으로 맞췄다. `tests/env-example.test.ts`가 문서값과 코드 기본값의 일치를 검사하므로 둘은 항상 함께 바꿔야 한다.
3. [docs/system-overview.md](../system-overview.md) 8단계의 상한 표와 낡은 환산치(주요 61건/일 → 65일 등)를 2026-09-21 측정값으로 고치고, 상한을 올려도 이미 밀려난 항목은 돌아오지 않는다는 점을 적었다.
4. [docs/plan.md](../plan.md)의 보존 정책을 새 값으로 갱신했다.

### 복구 적용 결과

`pnpm run restore:news -- --apply --confirm`을 실행했다. Git 이력의 shard와 리비전을 훑는 데 약 12분이 걸렸고, 보고서는 [reports/news-restore-apply.json](../../reports/news-restore-apply.json)에 있다.

| 버킷 | 복구 전 | 복구 후 | 가장 오래된 발행일 | 지금 무엇이 거는가 |
| --- | --- | --- | --- | --- |
| 주요 뉴스·공식 | 3,845 | 3,845 | 2026-06-26 (87일 전) | 90일 창 |
| 보조 뉴스 | 700 | 3,400 | 2026-07-28 (55일 전) | 상한 |
| 유튜브 | 500 | 500 | 2026-08-10 (42일 전) | 아직 여유 있음 |
| 전체 | 5,044 | 7,745 | | |

이력에서 찾은 밀려난 후보 6,635건 중 2,701건(보조 2,700, 주요 1)이 현재 관련도 규칙을 다시 통과해 돌아왔다. 나머지는 현재 규칙 미달 약 1,880건, 유튜브 약 1,760건(이 경로로는 복구 불가), 중복·창 밖 약 290건이다. 뉴스 묶음은 567 → 835개가 됐다.

되살릴 수 있는 것이 사실상 전부 보조 항목이다. 주요 항목은 상한이 아니라 창에 걸려 왔으므로 밀려난 적이 거의 없다. 복구 직후 보조는 새 상한 3,400건을 그대로 채웠고, 그래서 `전체` 범위는 55일에서 다시 상한이 걸린다. 그 시기(2026-07~08)의 보조 유입이 최근보다 많았기 때문이다. 90일까지 늘리려면 보조 상한을 5,000 이상으로 올리고 복구를 한 번 더 돌려야 한다.

수집 봇이 중간에 `main`에 커밋하면서 한 번 되돌아간 적이 있다. 봇은 `main`의 코드로 돌기 때문에 옛 상한으로 보존 정책을 다시 적용한다. 그래서 복구 결과를 병합하지 않고, 봇의 최신 데이터 위에서 복구를 다시 생성했다. 상한 변경을 push하기 전까지는 이 되돌림이 매시 반복된다.

효과는 다음 수집 실행부터 나타난다. 수집은 GitHub Actions가 `main`의 코드로 돌리므로, 이 변경을 push하기 전에는 운영 데이터가 그대로다. 기존 데이터는 상한이 올라가도 저절로 늘지 않고, 앞으로 들어오는 항목이 새 상한까지 쌓이는 방식으로 채워진다.

### 검증

- 측정은 저장소의 `data/items/` 88개 shard(5,044건)와 `lib/item-retention.ts`의 버킷 판정 규칙을 그대로 사용했다. 2026-09-21 13:5x KST, 로컬 macOS.
- snapshot 크기·검증 시간은 `lib/data-snapshot.ts`의 `serializeDataSnapshot`과 `dataBundleSchema.parse`로 실측했다.
- 파생 계산 비용은 `createFeedContext`를 현재 데이터와 2배·3배 복제 데이터로 실행해 측정했다. 복제 데이터는 id와 url만 바꿨으므로 유사도 분포가 실제와 다를 수 있다. 추정이다.
- C안 적용 후(2026-09-21 14:2x KST, macOS 26.6.2, Node v20.19.0): `pnpm test` 통과(357개 테스트 / 70개 스위트), `pnpm run typecheck` 통과, `pnpm run lint` 통과, `pnpm run validate:data` 통과(항목 5,044건). 상한만 올렸으므로 저장된 데이터는 그대로다.
- 복구 적용 후(2026-09-21 15:2x KST): `pnpm run validate:data` 통과(항목 7,745건, 묶음 835개, 묶인 항목 2,386건), `pnpm test` 통과(357개 테스트 / 70개 스위트). `data/collection-state.json`의 `totalItems`가 실제 항목 수와 맞는지도 이 검증에 포함된다.
