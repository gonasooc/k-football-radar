# W-002 · 보존 상한 인상 검토

- 상태: 진행 중
- 최근 갱신: 2026-09-21
- 관련 문서: [docs/README.md](../README.md), [docs/plan.md](../plan.md), [lib/item-retention.ts](../../lib/item-retention.ts), [docs/work/W-001-main-docs-structure.md](W-001-main-docs-structure.md)

## 현재 상황

보존 상한(주요 4,000 / 보조 700 / 유튜브 500)을 올려야 하는지 검토해 달라는 요청이다. 2026-09-21 기준 저장된 5,044건으로 실제 사용량, 유입량, 인상 비용을 측정했다.

핵심 결과는 세 버킷의 상황이 서로 다르다는 것이다. 주요 항목은 상한이 아니라 90일 창이 먼저 걸리므로 상한만 올려도 지금은 달라지지 않는다. 보조 항목은 20일, 유튜브는 45일치만 남아 있어 상한이 실제로 자르고 있다. 인상 비용은 작다. 아래 선택지에서 어디까지 올릴지 결정이 필요하다.

- 완료 조건: 상한을 유지할지 올릴지 결정하고, 올린다면 값 변경·과거 항목 복구 여부·관련 문서 갱신까지 끝낸다.
- 사람이 판단할 사항: 아래 선택지 A·B·C 중 하나. 특히 `전체` 범위와 유튜브를 90일까지 되돌릴지.

## 진행과 판단

### 배경과 범위

제품 정책은 발행 90일 보존이지만, 실제로는 종류별 건수 상한이 먼저 걸려 버킷마다 보이는 기간이 다르다. 이번 작업은 측정과 권고까지이고, 값 변경은 결정 후에 한다.

### 측정 결과

2026-09-21 기준. ‘유입량’은 상한에 잘리지 않은 구간만 사용했다(가장 오래된 날짜는 일부만 남아 있어 제외).

| 버킷 | 보유 / 상한 | 실제로 보이는 기간 | 무엇이 먼저 거는가 | 유입량 |
| --- | --- | --- | --- | --- |
| 주요 뉴스·공식 | 3,844 / 4,000 (96%) | 89.9일 | 90일 창 | 43.2건/일(90일 평균) |
| 보조 뉴스 | 700 / 700 (100%) | 20일 | 상한 | 35.1건/일 |
| 유튜브 | 500 / 500 (100%) | 45일 | 상한 | 11.2건/일 |

- 주요 항목의 상한 여유는 156건(4%)뿐이다. 지금은 창이 먼저 걸리지만 유입이 조금만 늘어도 상한이 먼저 걸린다.
- 유입량은 시기에 따라 크게 흔들린다. 일평균 주요 항목이 2026-07은 85.6건, 2026-08은 28.4건, 2026-09는 13.4건이다. 7월 수준이 돌아오면 90일을 채우는 데 약 7,800건이 필요하다.
- 90일을 온전히 채우려면 현재 유입 기준으로 주요 약 3,900건, 보조 약 3,200건, 유튜브 약 1,100건이 필요하다.

### 인상 비용

| 항목 | 현재(5,044건) | 3배 규모 추정 |
| --- | --- | --- |
| R2 snapshot 크기 | 6.27 MiB (항목당 약 1,303 bytes) | 약 18.6 MiB |
| 전체 Zod 검증 | 33 ms | 약 100 ms |
| SHA-256 계산 | 6 ms | 약 20 ms |
| `createFeedContext` 파생 계산 | 174 ms | 439 ms (실측, 거의 선형) |

항목 수를 2배·3배로 늘려 측정했을 때 파생 계산은 1.69배·2.53배로 선형에 가깝다. 제곱으로 늘어나는 구간은 없었다. 이 계산은 snapshot당 한 번, 요청 뒤에서 수행된다.

### 선택지

| 선택지 | 상한 | 보이는 기간 | 예상 항목 수 / snapshot |
| --- | --- | --- | --- |
| A. 유지 | 4,000 / 700 / 500 | 90일 / 20일 / 45일 | 5,044건 / 6.3 MiB |
| B. 단계적 인상 | 4,500 / 2,000 / 900 | 90일 / 57일 / 80일 | 약 6,800건 / 8.4 MiB |
| C. 90일 정합 | 6,000 / 3,400 / 1,200 | 세 버킷 모두 90일 | 약 8,500건 / 10.6 MiB |

권고는 C다. 제품 정책이 90일 보존인데 `전체` 범위와 유튜브만 20일·45일에서 잘리는 지금 상태가 문서·UI와 어긋나고, 비용은 snapshot 4.3 MiB와 파생 계산 약 100 ms 증가에 그친다. 7월 같은 뉴스 급증기까지 주요 항목을 방어하려면 주요 상한을 8,000으로 잡아야 하지만, 그 구간에서는 90일 창을 포기하고 최신성만 유지하는 선택도 가능하다.

C를 고르면 실행은 다음과 같다.

1. `lib/item-retention.ts`의 `DEFAULT_*` 상수를 바꾼다. 수집 워크플로에 보존 관련 환경변수가 없어서, 운영에 실제로 적용되는 값은 코드의 기본값이다.
2. 이미 밀려난 뉴스·공식 항목은 `pnpm run restore:news`로 Git 이력에서 되살릴 수 있다(dry-run 후 적용). 유튜브는 이 경로가 없고 `published_after`·`published_before`를 지정한 수집 워크플로 수동 실행으로 다시 채워야 한다.
3. 낡은 수치를 함께 고친다. [.env.example](../../.env.example)의 ‘주요 61건/일 → 약 65일, 보조 50건/일 → 약 14일’ 주석과 [docs/system-overview.md](../system-overview.md) 8단계의 같은 문장은 현재 측정과 다르다.
4. `pnpm run validate:data`와 `pnpm test`로 확인하고, 다음 수집 실행 후 `/api/health`와 화면에서 기간이 늘었는지 본다.

### 검증

- 측정은 저장소의 `data/items/` 88개 shard(5,044건)와 `lib/item-retention.ts`의 버킷 판정 규칙을 그대로 사용했다. 2026-09-21 13:5x KST, 로컬 macOS.
- snapshot 크기·검증 시간은 `lib/data-snapshot.ts`의 `serializeDataSnapshot`과 `dataBundleSchema.parse`로 실측했다.
- 파생 계산 비용은 `createFeedContext`를 현재 데이터와 2배·3배 복제 데이터로 실행해 측정했다. 복제 데이터는 id와 url만 바꿨으므로 유사도 분포가 실제와 다를 수 있다. 추정이다.
- 코드와 데이터는 바꾸지 않았다.
